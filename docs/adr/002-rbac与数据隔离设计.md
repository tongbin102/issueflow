# ADR 002: RBAC 与数据隔离设计

- 状态：**Accepted**（已采纳）
- 日期：2026-07-30
- 决策人：架构师 高见远 / 产品经理 许清楚

## 上下文（Context）

缺陷平台需区分四类角色，且各角色的数据可见范围不同：

- **提交者（SUBMITTER）**：仅应看到自己提交的问题，避免无关数据干扰。
- **开发人员（DEVELOPER）**：需全局查看问题以便认领与处理。
- **测试人员（TESTER）**：需全局查看问题以便执行验证。
- **管理员（ADMIN）**：全局可见，并承担用户/角色/流程/主题的配置职责。

核心矛盾：既要"精细化协作"（不同角色做不同动作），又要"数据范围隔离"（提交者不应看到他人问题）。

## 决策（Decision）

- **身份载体**：JWT payload 携带 `userId + roleCode`（外加 `jti` 用于黑名单）；无状态，每次请求由 `JwtAuthenticationFilter` 还原到 `SecurityContext`。
- **判定位置**：`Service` 层按 `roleCode` 判定数据范围与写权限，而非在 Controller 简单放行——
  - `SUBMITTER` 查询问题/看板/历史时**仅查 `reporter_id = 当前用户`**；其余角色查全部。
  - 编辑/删除问题限定"创建者或 ADMIN"（`IssueService.update/delete`）。
  - 用户/标签/系统配置等写操作限定 ADMIN（控制器内置 `requireAdmin()`）。
- **前端配合**：
  - 按钮级：`v-permission="['ADMIN']"` 指令按 `userStore.roles` 显隐。
  - 页面级：路由 `meta.roles` + 全局守卫（未登录跳 `/login`，角色不匹配跳 `/403`）。
- **单角色模型**：`user.role_id` 关联 `role` 表（无多对多），简化权限推导；`roles` 在登录/info 接口以数组返回（首位即主角色）。

## 后果（Consequences）

- **正向**：协作分工清晰；提交者数据严格隔离，提升隐私与聚焦度；判定集中在 Service 层，规则一致、易审计。
- **限制**：单角色模型不支持"一人多角色"，若未来需跨角色协作需扩展关联表。
- **风险点**：数据范围依赖 Service 层每个查询正确拼接 `reporter_id` 条件；新增查询时需显式处理 SUBMITTER 分支，防止越权。
- **已知边界**：提交者无法看到他人问题（含他人对其所提交问题的处理进展，仅能在自己问题详情中查看）。
